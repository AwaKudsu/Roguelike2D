# 简历包装与答辩

> 项目做完只完成了一半。**另一半是让别人知道你做了什么。** 这一半同样计入成绩和面试评价。

---

## 一、写进简历

### 1.1 简历条目模板

游戏项目放在「项目经历」栏，通常写 **3–5 条**。每条的结构是：**做了什么 + 用了什么技术 + 结果如何**。

❌ **反面写法**（90% 的学生这么写，毫无信息量）：

> **2D 肉鸽游戏**（课程作业）
> - 使用 Unity 开发了一款 2D 横板肉鸽游戏
> - 负责游戏的整体开发
> - 实现了游戏的核心玩法

✅ **正面写法**：

> **Roguelike2D — 2D 横板动作肉鸽游戏**　`Unity / C# / Git`　*个人项目*　[试玩](链接) | [源码](链接)
> - 独立设计并实现**房间模板池 + 方向匹配**的程序化关卡生成系统，支持固定种子复现，使同一关卡可被自动化测试验证
> - 设计**数据驱动的词条系统**（`ScriptableObject` + 多态效果类），新增 20+ 词条无需修改任何战斗代码，显著降低内容扩展成本
> - 实现动作手感细节：土狼时间、跳跃缓冲、可变跳跃高度、命中顿帧，将操作响应延迟感知降低至 0.1 s 以内
> - 通过**对象池**复用子弹与命中特效，将战斗中实例化次数从每帧 30+ 降至接近 0，帧率稳定在 60 FPS
> - 使用 Git 管理 5 周开发过程（60+ 次规范提交、5 个版本 tag），配置 **Unity SmartMerge** 解决场景合并冲突，使用 **Git LFS** 管理二进制素材

### 1.2 每一条都必须是「真做过」的

上面的写法每一条都对应一个**可验证的事实**。写的时候问自己：

- 我能说出这条的具体实现吗？（面试官一定会追问）
- 有代码/截图/数据能证明吗？

**⚠️ 绝对不要虚构**。面试官问「你这个对象池怎么实现的」而你答不上来，负面效果远大于不写这条。

### 1.3 量化数据怎么来

很多同学卡在「我没有数据可写」。数据是**测出来**的，不是想出来的：

| 想证明 | 怎么测 | 怎么写 |
| --- | --- | --- |
| 性能优化 | Unity Profiler 截图优化前后对比 | 「将 GC Alloc 从 2.4 KB/帧 降至 0.1 KB/帧」 |
| 代码规模 | `git ls-files "*.cs" \| xargs wc -l` | 「约 3500 行 C# 代码，20 个单元测试」 |
| 内容量 | 数一下 | 「5 种武器、24 个词条、6 种敌人、2 个 Boss」 |
| 开发过程 | `git log --oneline \| wc -l` | 「5 周内 68 次提交」 |
| 测试覆盖 | Unity Test Runner 界面截图 | 「20 个单元测试，覆盖战斗数值与关卡生成」 |

**⚡ 现在就去测，别等最后一天。** 尤其是 Profiler 截图——必须有「优化前」的对比，事后补不出来。

### 1.4 简历上的技术关键词

HR 和面试官会按关键词筛简历。下面这些词你的项目里确实有，**该写就写**：

`Unity` `C#` `面向对象设计` `设计模式（状态机 / 对象池 / 观察者）` `ScriptableObject 数据驱动` `程序化内容生成（PCG）` `Git 版本控制` `Git LFS` `单元测试` `性能优化（Profiler）` `UI 系统` `输入系统`

**注意**：写了 `设计模式`，就要能说出「我在哪里用了哪个模式，为什么」。说不出就别写。

### 1.5 简历首屏的「可试玩链接」

这是游戏项目相比其他项目的**最大优势**——面试官能直接玩。

必做：
1. GitHub 仓库设为 **Public**
2. 发一个 **Release**，上传打包好的 Windows zip
3. 有条件的话，出 **WebGL** 版部署到 **GitHub Pages**，简历里贴一个「点开即玩」的链接

> 一个能被点开的链接，比十行文字描述都有说服力。

## 二、答辩 PPT

### 2.1 结构（15–20 页，讲 10 分钟）

| 页 | 内容 | 时间 |
| --- | --- | --- |
| 1 | 封面：游戏名 + 你的名字 + 一句话简介 | 10 s |
| 2 | **演示视频**（60–90 秒，最重要的一页，放前面！） | 90 s |
| 3 | 游戏类型与核心体验（3 句话） | 30 s |
| 4 | **核心循环图**（局内 + 局外） | 60 s |
| 5 | 玩法展示：操作与战斗 | 45 s |
| 6 | 玩法展示：词条构筑（举一个 1+1>2 的例子） | 45 s |
| 7 | 玩法展示：关卡生成与 Boss | 45 s |
| 8 | **技术架构图**（分层） | 60 s |
| 9 | 技术亮点 1：数据驱动的词条系统 | 60 s |
| 10 | 技术亮点 2：程序化关卡生成 + 种子可复现 | 60 s |
| 11 | 技术亮点 3：手感调优的具体参数 | 45 s |
| 12 | 工程实践：Git 工作流 + 单元测试 | 45 s |
| 13 | 遇到的**最大困难**及解决过程 | 60 s |
| 14 | 数据：代码量 / 提交数 / 测试数 | 20 s |
| 15 | 不足与改进方向（**必讲，显专业**） | 40 s |
| 16 | 谢谢 + 试玩链接二维码 | 10 s |

### 2.2 三个关键建议

1. **第 2 页就放演示视频。** 老师看了一整天作业，先让他看到东西能动，印象分立刻不同。
2. **第 13 页「最大困难」是拿高分的关键。** 讲一个真实的技术难题 + 你的排查过程 + 最终方案。这体现的是**解决问题的能力**，而不是「我完成了功能」。
3. **第 15 页「不足」一定要讲，而且要讲得具体。** 「时间不够所以只做了 6 种敌人」不如「敌人 AI 目前是手写状态机，扩展到 15 种以上会大量重复代码，正确做法是抽象成可配置的行为树——这是我下一步的改进方向」。**后者叫工程判断力。**

## 三、老师/面试官最可能问的问题

### 技术类

| 问题 | 答题要点 |
| --- | --- |
| 你的关卡生成是怎么实现的？ | 讲清「房间池 + 方向匹配 + 权重随机 + 种子可复现」，最好能画出来 |
| 为什么用 ScriptableObject 存词条？ | 数据与逻辑分离；改数值不用重新编译；美术/策划也能配 |
| 你的敌人 AI 怎么写的？ | 三态状态机；为什么不用行为树（规模不够，过度设计） |
| 伤害是怎么算的？ | 加算与乘算的顺序；为什么先加后乘 |
| 怎么保证随机关卡不会出现死路？ | 入口/出口方向匹配校验；生成失败时重试 |
| 做过性能优化吗？ | 讲对象池 + Profiler 数据（**必须提前测好**） |
| 存档怎么做的？ | JSON + `persistentDataPath` + **版本号兼容** |
| 如果让你加多人联机，你会怎么做？ | 说清「现在架构哪里不支持」+「需要引入状态同步和权威服务器」——**承认现状比乱吹好** |

### 工程类

| 问题 | 答题要点 |
| --- | --- |
| 为什么用 Git？怎么用的？ | 讲分支策略、提交规范、每周 tag、SmartMerge 解决场景冲突 |
| 写过测试吗？ | 讲单元测试覆盖了什么（数值计算、种子可复现性），**这是最大加分项** |
| 项目里遇到最大的困难？ | 见 PPT 第 13 页，讲排查过程 |
| 如果重做一次，你会改什么？ | 提前想好一个真实的架构改进点 |
| 你在这个项目里学到了什么？ | 别说「学会了 Unity」，说「学会了用数据驱动的方式组织内容」这类可迁移的能力 |

## 四、答辩当天检查清单

```
□ 打包版在答辩电脑上跑通了（提前去试！U 盘 + 备用下载链接）
□ 演示视频本地存了一份（不依赖网络）
□ PPT 导出 PDF 备份（字体不会跑版）
□ GitHub 仓库是 Public 的，能打开
□ 演示用的存档已经准备好（别现场从零开始玩）
□ 手柄/键盘都测试过
□ 游戏音量调到合适（别炸麦）
□ 准备了「万一崩溃」的备用演示视频
```

## 五、做完之后

这个项目结束不代表价值结束。还可以：

1. **开源到 GitHub 并写一篇开发总结**（掘金/知乎/个人博客）—— 面试时可以主动分享
2. **发布到 itch.io** —— 「已发布」三个字的心理分量完全不同
3. **继续迭代成完整作品** —— 简历上从「课程作业」变成「独立游戏作品」
4. **参加 Game Jam** —— 48 小时做一个完整小游戏，是检验能力的最好方式，也是简历上的亮点

> 最重要的：**把这次踩过的坑写下来。** 面试时你讲不出「我用了什么技术」，但一定讲得出「我踩了什么坑、怎么爬出来的」——后者才是真正属于你的经验。
