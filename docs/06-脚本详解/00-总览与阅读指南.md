## 这个文件夹是什么

项目里目前有 **15 个手写脚本**，这里就有 **15 份文档**，一一对应。

每份文档回答四个问题：

1. **它解决什么问题** —— 如果没有它，会发生什么坏事
2. **代码怎么实现的** —— 逐行拆解，一行都不跳
3. **在 Unity 里怎么用** —— 挂在哪、填什么、和谁连接
4. **踩过什么坑** —— 真实的报错、真实的原因、真实的解法

### 依赖方向只有一个：上层依赖下层

```
控制层  ──依赖──▶  数据层
攻击层  ──依赖──▶  结算层 + 数据层
结算层  ──依赖──▶  数据层
流程层  ──依赖──▶  结算层
```

**反过来不成立。** 具体说：

- `Health.cs`（结算层）**不知道** `MeleeAttacker`（攻击层）存在
- `CharacterStats.cs`（数据层）**不知道**攻击是怎么打的
- `MeleeAttacker.cs` **不知道**打的是敌人还是木桶

> **这条规矩是整个项目最重要的架构约定。**
> 它带来一个直接好处：第 2 周加「法师火球」时，攻击层加一个新脚本就行，
> 结算层（`Health`、`HitReaction`）**一行都不用改**。

## 三、走一遍完整的数据流

理解这套架构最快的方法是**跟着一次按键走完全程**。

### 场景：玩家按下 `J` 攻击一个敌人

```
① 键盘按下 J
        │
        ▼
② PlayerInputActions（Unity 生成）识别到 Attack 动作
        │  触发 performed 事件
        ▼
③ PlayerInputReader.OnAttackPerformed()
        │  _attackPressedLatch = true;      ← 只是「记下来」，不做事
        │
        ▼
④ MeleeAttacker.Update()
        │  _input.ConsumeAttackPressed()    ← 「取走」那次按键
        │  检查冷却 GetCooldown(attackData)
        │
        ▼
⑤ MeleeAttacker.Execute(attackData)
        │  Physics2D.OverlapBoxAll(...)     ← 画出判定框，找出碰到的碰撞体
        │  对每个碰到的物体：TryGetComponent(out IDamageable target)
        │
        ▼
⑥ 读取数值（数据层）
        │  _stats.Get(StatType.Attack)          → 13
        │  _stats.Get(StatType.CritChance)      → 0.05
        │  伤害 = 13 × damageMultiplier × (暴击? 1.5 : 1)
        │
        ▼
⑦ 打包成 DamageInfo { Amount, SourcePosition, KnockbackForce, ... }
        │  target.TakeDamage(info)          ← 只认接口，不认具体类型
        │
        ▼
⑧ Health.TakeDamage(info)
        │  防御减伤：defense 0.1 → amount × 0.9
        │  Current -= amount
        │  _invincibilityTimer = 0.5f
        │  Damaged?.Invoke(info)            ← 广播事件
        │
        ├──────────────▶ ⑨ HitReaction.OnDamaged(info)
        │                   闪白 0.12s
        │                   硬直 0.18s（IsStunned = true）
        │                   击退：linearVelocity = away × 7
        │
        ▼
⑩ if (Current <= 0) Died?.Invoke()
        │
        ├──────────────▶ ⑪ EnemyController.OnDied()
        │                   _rb.simulated = false
        │                   Destroy(gameObject, 0.3f)
        │
        └──────────────▶ ⑫ RunManager.OnPlayerDied()（如果是玩家）
                            等待 1.5s → SceneManager.LoadScene(...)
```

### 这条链上每一环的「解耦点」

| 环节 | 解耦了什么 | 好处 |
|---|---|---|
| ③ 锁存按键 | 输入发生的时刻 vs 被处理的时刻 | 不丢帧、不重复 |
| ⑤ `IDamageable` | 「打」和「打的是什么」 | 加新敌人不用改攻击代码 |
| ⑥ `StatType` 枚举 | 数值的来源 vs 数值的使用 | 加装备不用改战斗代码 |
| ⑧ `event Damaged` | 扣血 vs 受击表现 | 加音效/飘字不用改 Health |
| ⑩ `event Died` | 死亡 vs 死亡后发生什么 | 加掉落/计分不用改 Health |

**这张表就是你能写在简历上的东西：**

> 使用事件驱动与接口抽象解耦战斗系统，
> 新增敌人类型 / 攻击方式 / 数值来源时，已有代码零修改。

## 四、几条贯穿全项目的设计约定

这几条不是「最佳实践」抄来的，是这个项目里**真实踩过坑之后定下来的**。

### 1. 数据放 `ScriptableObject`，逻辑放 `MonoBehaviour`

| 放什么 | 放在哪 | 例子 |
|---|---|---|
| 数值、配置 | `ScriptableObject` 资产（`ClassData`、`AttackData`） | 战士血量 140 |
| 行为、计算 | `MonoBehaviour` 组件（`Health`、`MeleeAttacker`） | 掉血、扣冷却 |

好处是**调数值不用改代码、不用重新编译**，策划（你）在 Inspector 里改完立刻生效。

### 2. 逻辑和表现分开

`Health` 只管「掉了多少血」，`HitReaction` 只管「看起来怎么样」。

两者靠一个 `event Damaged` 连接。所以：

- 想加受击音效 → 改 `HitReaction`，`Health` 一行不动
- 想改伤害公式 → 改 `Health`，`HitReaction` 一行不动

### 3. 事件订阅必须在 `OnEnable` / `OnDisable` 成对出现

```csharp
private void OnEnable()  => _health.Damaged += OnDamaged;
private void OnDisable() => _health.Damaged -= OnDamaged;
```

**为什么不用 `Start` / `OnDestroy`：**
物体被 `SetActive(false)` 时 `OnDestroy` 不会触发，但 `OnDisable` 会。
只加不减会导致「已销毁的对象仍然被事件调用」——
报错是 `MissingReferenceException`，而且很难定位。

### 4. `LayerMask` 留空不报错，是最阴险的 bug

`AttackData.targetLayers` 忘了勾 `Enemy`、`PlayerController.groundLayer` 忘了勾 `Ground`——
Unity **不会给任何提示**，Console 干净得像没事一样，只是功能静默失效。

> 所以本项目**每一个 `LayerMask` 字段都带一条以 `⚠️` 开头的 `[Tooltip]`**，例如：
> - `AttackData.targetLayers` → 「能打到的层。⚠️ 必须设成 Enemy，留空会永远打不到人」
> - `PlayerController.groundLayer` → 「⚠️ 必须选 Ground 层，留空会导致永远检测不到地面」
> - `EnemyController.playerLayer` → 「⚠️ 玩家所在的层，必须选 Player」
> - `DamageZone.targetLayers` → 「⚠️ 能伤到的层。要打到玩家就选 Player」
>
> 遇到「按键没反应」，**先看 Inspector 的层勾选，再看代码**。

### 5. 调试可视化不要删

`OnDrawGizmosSelected` 画的那些圆圈和方框（地面检测圆、敌人的三层感知圈、攻击判定框）
是后面几个月里**最省时间的工具**。

「打了没反应」→ 选中攻击者看一眼黄框在不在目标身上，2 秒定位问题。

## 六、维护约定

### 新增脚本时必须做的事

1. 在本文件夹新建 `<序号>-<脚本名>.md`（序号顺延）
2. 照 `_写作规范.md` 的七节结构写（**七个小节标题必须逐字照抄**）
3. 回到本文件的**第二节清单表**，加一行
4. 如果新脚本改变了架构分层，更新**第一节的架构图**
5. 同步到仓库并提交：

```powershell
Copy-Item 'C:\Users\hp\Desktop\Roguelike2D-脚本详解\*.md' 'D:\Roguelike2D\docs\06-脚本详解\' -Force
git -C D:\Roguelike2D add docs/06-脚本详解
git -C D:\Roguelike2D commit -m "docs(脚本): 补充 XXX 脚本详解"
```

> **这份文档集在两个地方各有一份**：
> 桌面的是「随手翻」的工作区，`D:\Roguelike2D\docs\06-脚本详解\` 是跟着 git 走的正式版。
> 桌面的丢了不可惜，**仓库里的那份丢了才是真丢了**。

### 脚本被修改时必须做的事

打开对应的 `.md`，找到讲那段代码的小节，同步更新。
同时在文档末尾的「最后更新」写上新的 Day 编号。

> **不要等**。改完代码顺手改文档只要 2 分钟，
> 攒到答辩前再补，就是对着一堆不认识的代码重新读一遍。
