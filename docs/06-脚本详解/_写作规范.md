# 脚本详解 · 写作规范

> 这份文件不是给人「读」的，是给「写」的看的。
> 它规定了本文件夹里每一份脚本解释文档必须长什么样。
> **以后每新增一个脚本，就照着这份规范写一份新的。**

---

## 一、这些文档写给谁看

写给项目作者本人。他需要能拿着这些文档做到三件事：

1. **复习** —— 隔两周回来看，能立刻想起当时为什么这么写
2. **答辩** —— 老师指着任何一个脚本问「这行是干嘛的」，能答得出来
3. **面试** —— 简历上写了这个项目，被追问技术细节时讲得清楚

所以验收标准只有一条：

> **一个没看过这个项目的人，读完这份文档，应该能自己把这个脚本重写出来。**

---

## 二、每份文档的固定结构

按顺序，**七个部分缺一不可**。每一节的标题**必须逐字照抄下面这七行**——
15 份文档要并排看，标题不一致就对不齐：

```markdown
## 一、头部信息表
## 二、一句话定位
## 三、为什么需要它
## 四、代码全解
## 五、在 Unity 里怎么配
## 六、踩过的坑
## 七、如果要改，改这里
```

> **额外的补充章节**（比如「相关文档」「最重要的三条规则」）用**不带编号**的 `## ` 标题，
> 插在合适的位置。编号只留给上面这七节。

### 2. 一句话定位

一句话说清它是干什么的。不超过 40 字。

### 3. 为什么需要它（最重要的一节）

**讲问题，不讲代码。**

要回答的是：「如果不存在这个脚本，会发生什么？」

好的写法是先描述一个具体的坏结果，再引出设计：

> 如果没有 `IDamageable` 这个接口，`MeleeAttacker` 就得写这样的代码：
>
> ```csharp
> if (hit.TryGetComponent(out EnemyController enemy)) enemy.TakeDamage(dmg);
> else if (hit.TryGetComponent(out PlayerController player)) player.TakeDamage(dmg);
> else if (hit.TryGetComponent(out Barrel barrel)) barrel.Break();
> ```
>
> 每加一种能被打的东西，就要回来改这个 `if` 链。
> 而接口把「我打的东西能挨打」这件事，和「它是敌人还是木桶」彻底拆开了。

这一节决定了读者理解的是「一段代码」还是「一个设计」。

### 4. 代码全解

本文档的主体。规格见第三节。

### 5. 在 Unity 里怎么配

如果这个脚本需要挂到物体上、需要拖引用、需要在 Inspector 填值——把配置步骤写清楚，**包括每个字段应该填什么、为什么**。

不需要配置的脚本（比如纯枚举、纯接口）这一节写「本脚本不需要挂在任何物体上」。

### 6. 踩过的坑

只写**真实踩过的**。格式固定：

> **现象**：……
> **根因**：……
> **解法**：……

没踩过就写「暂无」。**不要为了凑内容编坑。**

### 7. 如果要改，改这里

列出最可能被修改的几个点，以及改的时候要注意什么。
比如「想把跳跃改成二段跳，需要在 XXX 处加 YYY」。

## 三、「代码全解」这一节的规格

这是用户明确要求的重点：**每行的意义是什么**。

### 3.1 分块

按代码里的 `// ---------------- 分节标题 ----------------` 注释分段。
如果代码里没有分节注释，就按「字段区 / 生命周期方法 / 公开方法 / 私有方法 / 调试」自己分段。

### 3.2 每一块的写法

**第一步：贴代码。** 带行号，和源文件一致：

```csharp
106:     private void CheckGround()
107:     {
108:         // 用圆形重叠检测，而不是 OnCollisionEnter —— 后者会把自己撞墙、撞天花板也算成「落地」
109:         IsGrounded = Physics2D.OverlapCircle(GroundCheckPoint, groundCheckRadius, groundLayer);
110:     }
```

**第二步：逐行解释。** 用表格或者列表，**一行都不能跳过**：

| 行 | 代码 | 含义 |
|---|---|---|
| 106 | `private void CheckGround()` | 声明一个私有方法，只有本脚本内部能调用。放在 `FixedUpdate` 里每物理帧调一次 |
| 109 | `Physics2D.OverlapCircle(...)` | 在 `GroundCheckPoint` 画一个半径 `groundCheckRadius` 的圆，只检查 `groundLayer` 层上的碰撞体。返回第一个碰到的 `Collider2D`，没碰到返回 `null`。`null` 会被隐式转换成 `false`，所以能直接赋给 `bool` |

**第三步：关键决策。** 这一段代码里如果有「不这么写会怎样」的地方，单独拎出来讲：

> **为什么不用 `OnCollisionEnter2D`？**
> 因为它只告诉你「撞到了东西」，不告诉你「从哪个方向撞的」。
> 角色跳起来撞到天花板、走路撞到墙，都会触发 `OnCollisionEnter2D`——
> 如果你拿它来判断落地，角色会贴在墙上就能无限跳。

### 3.3 禁止事项

- ❌ **不许写「等等」「省略」「以此类推」** —— 用户要的就是完整
- ❌ **不许编造代码里没有的东西** —— 必须对着真实源文件写
- ❌ **不许只翻译代码字面意思** —— `float x = 1f;` 不能解释成「定义浮点变量 x 等于 1」，要解释它在这里代表什么
- ❌ **不许跳过「显而易见」的行** —— 对新手来说没有显而易见的行
- ✅ 允许并鼓励讲 C# 语言本身的语法（`=>`、`?.`、`out`、`readonly`、`ref`），因为读者是学生，正好是复习

## 四、语言风格

- **第二人称**，直接对读者说「你」
- **先讲为什么，再讲是什么**，最后才是怎么用
- **用具体的数字和场景**，不用「比较大的值」这种模糊说法，要写「0.15 太大会导致还没落地就算落地」
- **比喻可以有，但要克制**，一个概念最多一个比喻
- **术语第一次出现时给中文解释**：`Gizmos（场景视图里的调试线条）`
- 中文和英文/代码之间加空格：`在 Scene 视图里画一个圆`，不是 `在Scene视图里画一个圆`

---

## 五、格式约定

- 中文标点用全角：，。：；「」—— 不用 , . : ;
- 代码块必须标语言：```csharp ```markdown ```powershell
- 表格用 Markdown 表格
- 引用用 `>`，用来放「注意」「为什么」「坑」
- 文件路径用反引号包起来，写完整路径

## 六、新增脚本时的流程

1. 在 `D:\Roguelike2D\Assets\_Project\Scripts\` 下写好脚本
2. 在本文件夹按**下一个序号**新建 `<NN>-<脚本名>.md`
3. 照着上面七节结构写
4. 回到 `00-总览与阅读指南.md`，把新文件加进清单表

**序号规则**：按**依赖顺序**排，不按写代码的时间顺序。
底层的（枚举、数据）在前，上层的（控制、流程）在后。
